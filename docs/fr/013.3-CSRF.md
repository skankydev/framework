# 13.3 CSRF

Le CSRF, c'est le piège où un site tiers fait envoyer une requête à ton appli par le navigateur d'un utilisateur connecté. Pour s'en protéger, j'ai mis en place un token par session, comparé à chaque requête qui modifie quelque chose (le principe du *synchronizer token*).

C'est le `CsrfMiddleware` qui s'en charge, un des deux middlewares globaux par défaut (avec `Session`, qui passe juste avant lui : il faut une session démarrée pour lire et écrire le token, voir [07 Les Middlewares](007-Les-Middlewares.md)). Bref, la plupart du temps, t'as rien à faire.

## Ce qu'il vérifie, et quand

Seulement les méthodes qui modifient quelque chose : `POST`, `PUT`, `PATCH`, `DELETE`. Un `GET`, jamais : le CSRF a de sens que sur une action qui change quelque chose côté serveur.

Le token envoyé est cherché à deux endroits, dans cet ordre :

1. le champ `_token` de l'input (un formulaire classique) ;
2. sinon le header `X-CSRF-Token` (l'AJAX).

## Le cas form vs le cas AJAX

**Formulaire** : rien à faire. `FormBuilder::open()` ajoute `csrf_field()` tout seul dans toute balise `<form>` en méthode POST : un champ caché `_token` avec la valeur courante.

Le token est créé une seule fois par session, la première fois qu'on le demande, puis réutilisé tant que la session vit. C'est pas un token jetable à chaque requête.

**AJAX** : là, c'est à toi. Le framework te donne la brique serveur (`csrf_token()`, et il accepte le header `X-CSRF-Token`), mais câbler l'envoi automatique de ce header sur chaque `fetch`, c'est le boulot de l'application. La méthode classique : mettre le token dans une balise `<meta name="csrf-token">` du layout, puis wrapper `fetch` côté projet pour qu'il lise cette balise et ajoute le header.

## En cas d'échec

Comme pour les autres middlewares de garde ([07](007-Les-Middlewares.md)), la réponse dépend de qui appelle :

- le client attend du JSON (`wantsJson()`, voir [05](005-La-Requete-Client.md)) : un **419** en JSON (`{"ok": false, "error": "..."}`) ;
- sinon : une redirection vers la page précédente (`Referer`, ou `/` à défaut) avec un flash d'erreur (`withFlash('error', ...)`, voir [09 Les Réponses](009-Les-Reponses.md)).

Dans les deux cas, le controller est jamais atteint : le middleware court-circuite en retournant une `Response` au lieu d'appeler `$next()`.

## Sous le capot

```php
private const UNSAFE = ['POST', 'PUT', 'PATCH', 'DELETE'];
```

Le token soumis est comparé à celui de la session avec `hash_equals()`, une comparaison à temps constant, pas un `===` naïf. Comme ça, pas de *timing attack* sur la comparaison elle-même.

```php
function csrf_token(): string {
    $token = Session::get('csrf_token');
    if (!is_string($token) || $token === '') {
        $token = (new Token())->getToken();
        Session::set('csrf_token', $token);
    }
    return $token;
}
```
