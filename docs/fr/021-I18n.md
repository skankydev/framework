# 21 L'internationalisation (i18n)

Pour traduire l'interface, SkankyDev s'appuie sur **ext/intl** (ICU), pas sur gettext. Gettext dépend des locales installées sur le système, garde les `.mo` en cache jusqu'au redémarrage de PHP, et ses pluriels sont limités. Intl formate les messages, les nombres et les dates proprement, mais ne range pas les traductions : ça, c'est le `Translator` du framework, avec de simples fichiers PHP.

Ce chapitre couvre la traduction de l'**interface** (les libellés, les messages). Le contenu (un article de blog en plusieurs langues) est un autre sujet, qui se règle dans tes Documents.

## Traduire

```php
<dt><?= __('admin.blog.title') ?></dt>
<dd><?= e($post->name) ?></dd>

<p><?= __('blog.post.by', ['name' => e($post->author)]) ?></p>
```

`__()` retourne **toujours une string**. Si la clé n'existe pas (ou si le message est mal écrit), tu récupères la clé elle-même, `blog.post.by` : la page s'affiche quand même, et on voit tout de suite ce qui manque. En debug, c'est aussi écrit dans `logs/{date}-i18n.log`.

`__()` ne fait **aucun échappement** : le texte des fichiers de langue est à toi, c'est sûr, mais un argument qui vient de l'utilisateur doit passer par `e()`, comme partout ailleurs.

## Les fichiers de langue

Ils sont dans `src_front/lang/` (`i18n.path`, constante `LANG_FOLDER`), un dossier par langue, **un fichier par domaine**. Le premier segment de la clé, c'est le fichier :

```
src_front/lang/
  fr/
    app.php        __('app.welcome')
    blog.php       __('blog.post.count')
  en/
    app.php
    blog.php
```

```php
// src_front/lang/fr/blog.php
return [
    'label' => 'Titre',
    'post'  => [
        'title' => 'Article : {title}',
        'count' => '{count, plural, =0 {Aucun article} one {# article} other {# articles}}',
        'by'    => '{gender, select, female {Écrite par {name}} other {Écrit par {name}}}',
    ],
];
```

La suite de la clé suit la notation à points habituelle (comme `Config::get()`). Un fichier n'est chargé que si on en a besoin, et une seule fois par requête.

### Une clé = un usage, pas un mot

La clé identifie un endroit de l'interface, la valeur contient le texte exact à afficher, majuscules comprises. Pas de `Title` / `title` en double : si tu as besoin des deux, c'est que tu as deux usages, donc deux clés.

Et surtout, **on traduit des phrases entières**, jamais des morceaux qu'on recolle :

```php
// ❌ marche en français, casse dans d'autres langues (ordre des mots, accords)
__('word.the') . ' ' . __('word.field') . ' ' . __('word.required')

// ✅
'required' => 'Le champ {field} est requis',
```

Pour une transformation purement visuelle (un titre en capitales), c'est le CSS (`text-transform`), pas une nouvelle clé.

## Le format ICU MessageFormat

Les messages sont au format ICU, le même que Symfony ou `intl-messageformat` en JS :

- **`{name}`** : une variable, une seule accolade (pas de `:name` comme Laravel).
- **`{count, plural, one {...} other {...}}`** : les pluriels. `#` est remplacé par le nombre, formaté selon la locale (`1 234` en fr, `1,234` en en). Les règles viennent de CLDR, il n'y a rien à coder : **en français, `0` est au singulier** (« 0 article »), en anglais non (« 0 posts »). `=0 {...}` force un texte pour une valeur précise.
- **`{gender, select, female {...} other {...}}`** : un choix sur une valeur. `other` est obligatoire.

Un piège : en ICU, **l'apostrophe droite `'` est un caractère d'échappement**. `l'article` passe, mais `'{name}'` s'affiche tel quel, sans remplacer la variable. Le plus simple : utilise l'apostrophe typographique `’` dans tes traductions, et le problème n'existe plus.

## Garder les fichiers à jour : `lang-sync`

Plutôt que de recopier les clés à la main dans chaque langue, `php craft lang-sync` lit ton code et met les fichiers de langue à jour :

```bash
php craft lang-sync              # ajoute les clés manquantes
php craft lang-sync --dry-run    # montre ce qu'il ferait, sans rien écrire
php craft lang-sync --prune      # supprime aussi les clés inutilisées
php craft lang-sync --check      # n'écrit rien, sort en erreur s'il manque quelque chose (pour la CI)
```

Il scanne `src/{Module}/` de chaque module et le dossier de vues, et trouve tous les `__('domaine.cle')`. Pour chaque langue de `i18n.available` (et le fallback), il ajoute les clés manquantes dans `lang/{langue}/{domaine}.php` avec la valeur **`null`** :

```php
return [
    'title' => 'Titre',
    'post'  => [
        'count' => null,
    ],
];
```

`null` veut dire « pas encore traduit » : le `Translator` passe à la langue de secours, puis à la clé brute, donc ça se voit tout de suite sur la page. À chaque passage, la commande te liste ce qui reste à traduire.

Quelques règles à connaître :

- **Les clés construites à l'exécution** (`__('status.' . $status)`, `__($key)`) ne peuvent pas être devinées. La commande les liste avec leur fichier et leur ligne. Quand il y a un préfixe littéral (`status.`), les clés qui commencent par lui ne sont jamais considérées comme inutilisées.
- **Une clé inutilisée n'est jamais supprimée sans `--prune`**, justement à cause des clés dynamiques : « inutilisée » veut parfois dire « utilisée, mais invisible au scan ».
- **Le domaine `skankydev` n'est jamais touché** : c'est celui du framework.
- **Les dossiers régionaux** (`fr_CA/`) ne sont pas synchronisés : ils ne contiennent que des écarts.
- Le fichier est réécrit : le docblock d'en-tête est conservé, l'ordre des clés aussi, mais **les commentaires à l'intérieur du tableau sont perdus**.

## Locale et langue

On distingue deux choses :

- la **langue** (`fr`) choisit le catalogue, donc le dossier ;
- la **locale** complète (`fr_CA`) sert au formatage : nombres, dates, devises, le `#` des pluriels.

Quand une clé est cherchée avec la locale `fr_CA`, le `Translator` essaie dans l'ordre :

```
lang/fr_CA/blog.php    optionnel : seulement les écarts québécois
lang/fr/blog.php       le catalogue principal
lang/{fallback}/...    la langue de secours (i18n.fallback)
la clé brute
```

En pratique, tu n'as que des dossiers `fr/` et `en/`. Le jour où le Québec a besoin d'un mot différent, tu crées `fr_CA/blog.php` avec juste ce mot, et rien d'autre ne change.

Les locales s'écrivent au **format ICU**, `fr_FR` (avec un underscore). Le web, lui, utilise le format **BCP 47**, `fr-FR` (avec un tiret) : l'attribut `lang` du HTML, le header `Accept-Language`, `Intl` en JS. `Translator::setLocale()` accepte les deux, et `Translator::toLanguageTag()` (ou `$this->htmlLang()` dans une vue) fait la conversion inverse.

## La config

```php
'i18n' => [
    'locale'    => 'en_US',              // locale par défaut
    'fallback'  => 'en',                 // langue de secours quand une clé manque
    'available' => ['en_US'],            // ce que ton projet accepte
    'path'      => LANG_FOLDER,          // src_front/lang
],
```

Ce sont les défauts du framework : **l'anglais**. Le starter accepte en plus le français (`'available' => ['en_US', 'fr_FR']`). Pour un projet en français, remets `'locale' => 'fr_FR'` et `'fallback' => 'fr'` dans ton `master.config.php`.

Attention à `available` : la config est fusionnée par `array_replace_recursive` ([04 Config](004-Config.md)), donc une liste est fusionnée **index par index**. Le défaut du framework n'a qu'un élément pour que ta liste le remplace sans surprise.

## Choisir la langue

Le framework fournit les outils, **c'est ton application qui décide** où et comment s'en servir. Le starter le fait dans `config/bootstrap.php` :

```php
Translator::setLocale(LocaleNegotiator::negotiate());
```

`LocaleNegotiator::negotiate()` lit le header `Accept-Language`, respecte l'ordre de préférence (`q`), et retourne la meilleure locale de `i18n.available`, telle qu'elle est écrite dans ta config. Une langue demandée sans région (`fr`) ou avec une autre région (`fr-CA`) trouve `fr_FR`. Si rien ne correspond, c'est `i18n.locale`. En CLI, pas de header, donc la locale par défaut.

On n'utilise pas `Locale::acceptFromHttp()` (elle renvoie la préférence du navigateur sans tenir compte de ce que tu as), ni `Locale::lookup()` (elle ne trouve pas `fr_FR` quand on demande `fr`, et renvoie la valeur en minuscules).

Pour un **sélecteur de langue**, déplace l'appel dans un middleware ([07](007-Les-Middlewares.md)) placé **après** `Session` : le bootstrap tourne avant que la session soit démarrée.

```php
class LocaleMiddleware implements MiddlewareInterface {
    public function handle(Request $request, callable $next): mixed {
        Translator::setLocale(Session::get('locale') ?? LocaleNegotiator::negotiate());
        return $next($request);
    }
}
```

## Les helpers de vue

`HtmlView` embarque le trait `TranslatorHelper`, pour tout ce qui dépend de la locale (ici avec `fr_FR`) :

```php
<html lang="<?= $this->htmlLang() ?>">          <!-- fr-FR -->

<?= $this->number(1234.5) ?>                     <!-- 1 234,5 -->
<?= $this->number(3.1, 2) ?>                     <!-- 3,10 -->
<?= $this->currency(12.5) ?>                     <!-- 12,50 € -->
<?= $this->currency(12.5, 'GBP') ?>              <!-- 12,50 £GB -->
<?= $this->date($post->created) ?>               <!-- 12 oct. 2026 -->
<?= $this->date($post->created, pattern: 'd MMMM y') ?>  <!-- 12 octobre 2026 -->
```

`date()` accepte un `DateTimeInterface`, une date Mongo (`UTCDateTime`), un timestamp ou une chaîne, et utilise la timezone par défaut (`timeHelper.timezone`). Les styles sont les constantes de `IntlDateFormatter` (`SHORT`, `MEDIUM`, `LONG`, `FULL`, `NONE`), un `pattern` ICU passe devant.

## Les messages du framework

Tout ce que le framework affiche à un utilisateur passe aussi par `__()`, dans le domaine réservé **`skankydev`** : les messages de validation ([12.2](012.2-La-Validation.md)), les erreurs d'upload ([05](005-La-Requete-Client.md)), les messages des middlewares (connexion requise, CSRF, trop de tentatives...) et toute la sortie de `php craft` ([16](016-Craft-et-CLI.md)). Ils sont livrés en anglais et en français dans `Publishable/lang/`.

Deux exceptions, volontaires, qui restent **en anglais, en dur** :

- **les messages d'exception et les logs** : ils sont écrits pour le développeur, et une stack trace se partage et se cherche mieux en anglais ;
- **les pages d'erreur** (`error/production.php`, `error/404.php`, `error/debug.php`) : elles s'affichent justement quand quelque chose a planté. Si elles passaient par `__()`, un fichier de langue cassé (une erreur de syntaxe, par exemple) planterait aussi la page d'erreur, et on tournerait en boucle. Pour les avoir en français, publie-les (`php craft publish -p=error`) et écris-les comme tu veux.

C'est le seul domaine avec un repli : tant que tu n'as pas de `skankydev.php` dans ton dossier de langues, le `Translator` lit celui du framework. Pour les personnaliser ([16 Craft et CLI](016-Craft-et-CLI.md)) :

```bash
php craft publish -p=lang
```

Ta copie remplace **le fichier entier** de la langue concernée, pas clé par clé : garde toutes les clés dedans. Conséquence : quand une mise à jour du framework ajoute des messages, ta copie ne les a pas, et tu verras leurs clés brutes (`skankydev.cli.done`) à la place du texte. Il faut alors republier et reporter tes retouches. Et pour une langue que le framework ne livre pas (l'allemand, par exemple), c'est pareil : crée `de/skankydev.php`.

## Et le front ?

Attention si tu veux réutiliser ces traductions côté Vue : **vue-i18n n'utilise pas ICU** (ses pluriels s'écrivent avec des `|`). Pour garder un seul format, la piste est `intl-messageformat` (FormatJS) côté front, alimenté par une route qui sert les catalogues en JSON. Ce n'est pas encore fait.
