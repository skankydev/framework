# 09.3 Relations et propagation

Deux mécanismes distincts, tous les deux déclarés côté `MasterCollection` (jamais côté Document) :

- **les relations** (`belongsTo` / `hasMany`) : lire un document lié, sans requête manuelle ni `$lookup`.
- **la propagation** : garder à jour les `EmbeddedSnapshot` ([09.1](009.1-Persistable.md)) éparpillées dans d'autres collections quand la source change.

## belongsTo / hasMany

Tu déclares tes relations dans `relations()`, sur la Collection :

```php
class PostCollection extends MasterCollection {
    public function relations(): array {
        return [
            'user'     => ['type' => 'belongsTo', 'collection' => UserCollection::class, 'key' => 'user_id'],
            'comments' => ['type' => 'hasMany',   'collection' => CommentCollection::class, 'key' => 'post_id'],
        ];
    }
}
```

- `belongsTo` : la clé (`user_id`) est **sur ce document** (`Post`) et pointe vers l'autre (`User`). Tu récupères un document, ou `null`.
- `hasMany` : la clé (`post_id`) est **sur l'autre document** (`Comment`) et pointe vers celui-ci. Tu récupères un tableau (vide s'il n'y a rien).

Le nom de la relation (`'user'`, `'comments'`) est ce que tu lis sur le document, comme une propriété normale :

```php
$post->user;      // une instance de User, ou null
$post->comments;  // un tableau de Comment
```

### Chargement paresseux, et en masse

Sans rien demander, `$post->user` charge la relation **à la demande** (une requête au premier accès) et la garde en cache sur l'instance : lire deux fois `$post->user` ne fait pas deux requêtes. Pratique, mais dans une boucle sur des posts, ça fait une requête par post (le classique N+1).

Pour l'éviter, précharge en masse avec `with`. Une seule requête par relation, peu importe le nombre de documents :

```php
$collection->find($filter, ['with' => ['user', 'comments']]);
$collection->findOne($filter, ['with' => ['user']]);
$collection->findById($id, ['with' => ['user']]);
$collection->paginate($filter, $paginateInfo, ['user']); // 3e argument dédié
```

Si tu te trompes (relation inconnue, ou `type` qui n'est ni `belongsTo` ni `hasMany`), ça lève tout de suite une `\InvalidArgumentException`, au lieu de te renvoyer un `null` ou un `[]` silencieux. Comme ça, une faute de frappe dans `with` se voit au premier test, pas en prod sous la forme d'un « champ vide » inexplicable.

Une relation chargée n'est ni sauvée ni « sale » : elle n'apparaît pas dans le JSON ni dans ce qui part en base, et elle n'a aucun effet sur `isDirty()`.

### Le CrudMaker les déclare déjà

Pour chaque champ `ObjectId` d'un Document généré par `crud-maker`, la Collection reçoit automatiquement l'entrée `belongsTo` correspondante, et le controller précharge la relation dans `index()` avec `with`. Pour le cas standard (une clé étrangère simple), tu n'as rien à écrire à la main.

## Propagation des EmbeddedSnapshot

Une Collection déclare où ses documents sont embarqués ailleurs avec `embeddedIn()` :

```php
class UserCollection extends MasterCollection {
    public function embeddedIn(): array {
        return [
            [
                'collection' => PostCollection::class,
                'field'      => 'author',
                'class'      => UserSnapshot::class,
                'sync'       => true,     // par défaut : tout de suite, sinon direction la Queue
                'onDelete'   => 'keep',   // 'keep' (défaut) | 'mark' | 'unset'
            ],
        ];
    }
}
```

- `collection` / `field` : où chercher les snapshots à corriger (`Post.author`).
- `class` : la classe `EmbeddedSnapshot` utilisée là-bas.
- `sync` : à `true`, la resynchronisation se fait tout de suite, dans la requête qui a fait l'update. À `false`, elle est poussée sur la Queue ([17](017-Queue-et-Jobs.md)) et la requête courante n'attend pas.
- `onDelete` : ce qui arrive aux snapshots existantes quand le `User` source est supprimé :
  - `keep` (défaut) : rien, la snapshot reste figée (l'auteur d'un post supprimé garde son nom affiché).
  - `mark` : `_deleted` passe à `true` sur la snapshot (tu peux afficher « utilisateur supprimé », par exemple).
  - `unset` : le champ (`author`) est carrément retiré du document cible.

### Quand ça se déclenche

Automatiquement, tu n'appelles rien toi-même :

- **update** d'un `User` : si les champs modifiés (`getDirty()`) touchent un champ copié par la snapshot (`UserSnapshot::syncedFields()`), la propagation part. Changer un champ non copié (le mot de passe, par exemple) ne déclenche rien.
- **delete** (`deleteOne`, `deleteById`, ou en masse avec `delete($filter)`) : `onDelete` s'applique, sauf s'il vaut `keep` (rien à faire dans ce cas).

Dans les deux cas, c'est un `SnapshotSyncJob` par cible (`collection` / `field`) qui fait le travail : tout de suite si `sync`, ou via la Queue sinon.

`syncIndexes()` (appelé par `db-sync`, [16 Craft et CLI](016-Craft-et-CLI.md)) crée tout seul un index sur `{field}._id` côté cible pour chaque entrée d'`embeddedIn()`. La propagation en a besoin pour retrouver les snapshots rapidement.

## Sous le capot

- **Le cache des relations.** Une relation chargée (via `with` ou paresseusement) vit dans une `WeakMap` à part, comme l'état du dirty tracking ([09 Model](009-Model.md)). C'est pour ça qu'elle est absente de `bsonSerialize()` et `jsonSerialize()` et sans impact sur `isDirty()`.
- **Ce que fait le job.** `SnapshotSyncJob` **relit la source** au moment où il tourne, il ne transporte pas la snapshot. Si le `User` existe encore, il reconstruit `UserSnapshot` et fait un `updateMany` sur tous les documents qui portent son `_id` dans `author._id`. S'il a disparu, `onDelete` s'applique. Ça le rend idempotent et insensible à l'ordre : le dernier passage écrit toujours l'état courant, même si plusieurs jobs pour le même `User` s'empilent dans la Queue.
- **Pas de cascade.** `updateMany()`, utilisé par le job, contourne les behaviors et la propagation. C'est voulu : sinon un `SnapshotSyncJob` qui met à jour des `Post` pourrait redéclencher une propagation en cascade.
