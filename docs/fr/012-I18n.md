# 12 L'internationalisation

Pour traduire l'interface, SkankyDev s'appuie sur **ext/intl** (ICU). Intl sait formater les messages, les nombres et les dates proprement, mais il range pas les traductions : ça, c'est le boulot du `Translator` du framework, avec de simples fichiers PHP.

On parle ici de la traduction de l'**interface** (les libellés, les messages). Le contenu (un article de blog en plusieurs langues), c'est une autre histoire, et ça se règle dans tes Documents.

## Traduire

```php
<dt><?= __('admin.blog.title') ?></dt>
<dd><?= e($post->name) ?></dd>

<p><?= __('blog.post.by', ['name' => e($post->author->name), 'gender' => $post->author->gender]) ?></p>
```

`__()` te rend **toujours une string**. Si la clé existe pas (ou si le message est mal écrit), tu récupères la clé elle-même, `blog.post.by` : la page s'affiche quand même, et tu vois direct ce qui manque. En debug, c'est aussi noté dans `logs/{date}-i18n.log`.

`__()` fait **aucun échappement** : le texte des fichiers de langue, c'est toi qui l'écris, donc pas de souci. Par contre un argument qui vient de l'utilisateur passe par `e()`, comme partout ailleurs.

## Les fichiers de langue

Ils sont dans `src_front/lang/` (`i18n.path`, constante `LANG_FOLDER`), un dossier par langue, **un fichier par domaine**. Le premier segment de la clé, c'est le fichier :

```
src_front/lang/
  fr/
    app.php        __('app.welcome')
    blog.php       __('blog.post.count')
  en/
    app.php
    blog.php
```

```php
// src_front/lang/fr/blog.php
return [
    'label' => 'Titre',
    'post'  => [
        'title' => 'Article : {title}',
        'count' => '{count, plural, =0 {Aucun article} one {# article} other {# articles}}',
        'by'    => '{gender, select, female {Écrite par {name}} other {Écrit par {name}}}',
    ],
];
```

La suite de la clé, c'est la notation à points habituelle (comme `Config::get()`). Un fichier est chargé seulement quand on en a besoin, et une seule fois par requête.

### Une clé = un usage, pas un mot

La clé, c'est un endroit de l'interface. La valeur, c'est le texte exact à afficher, majuscules comprises. Pas de `Title` / `title` en double : si t'as besoin des deux, c'est que t'as deux usages, donc deux clés.

Et surtout, **on traduit des phrases entières**, jamais des morceaux qu'on recolle :

```php
// ❌ marche en français, casse dans d'autres langues (ordre des mots, accords)
__('word.the') . ' ' . __('word.field') . ' ' . __('word.required')

// ✅
'required' => 'Le champ {field} est requis',
```

Pour un truc purement visuel (un titre en capitales), c'est le CSS (`text-transform`), pas une nouvelle clé.

## Le format ICU MessageFormat

Les messages sont au format ICU, le même que Symfony ou `intl-messageformat` en JS :

- **`{name}`** : une variable, une seule accolade (pas de `:name` comme Laravel).
- **`{count, plural, one {...} other {...}}`** : les pluriels. `#` est remplacé par le nombre, formaté selon la locale (`1 234` en fr, `1,234` en en). Les règles viennent de CLDR, t'as rien à coder : **en français, `0` est au singulier** (« 0 article »), en anglais non (« 0 posts »). `=0 {...}` force un texte pour une valeur précise.
- **`{gender, select, female {...} other {...}}`** : un choix sur une valeur. `other` est obligatoire.

Attention au piège : en ICU, **l'apostrophe droite `'` est un caractère d'échappement**. `l'article` passe, mais `'{name}'` s'affiche tel quel, sans remplacer la variable. Le plus simple : utilise l'apostrophe typographique `’` dans tes traductions, et le problème existe plus.

## Garder les fichiers à jour : `lang-sync`

Recopier les clés à la main dans chaque langue, c'est pénible. `php craft lang-sync` lit ton code et met les fichiers de langue à jour pour toi :

```bash
php craft lang-sync              # ajoute les clés manquantes
php craft lang-sync --dry-run    # montre ce qu'il ferait, sans rien écrire
php craft lang-sync --prune      # supprime aussi les clés inutilisées
php craft lang-sync --check      # n'écrit rien, sort en erreur s'il manque quelque chose (pour la CI)
```

Il scanne `src/{Module}/` de chaque module et le dossier de vues, et récupère tous les `__('domaine.cle')`. Pour chaque langue de `i18n.available` (et le fallback), il ajoute les clés manquantes dans `lang/{langue}/{domaine}.php` avec la valeur **`null`** :

```php
return [
    'title' => 'Titre',
    'post'  => [
        'count' => null,
    ],
];
```

`null`, ça veut dire « pas encore traduit » : le `Translator` passe à la langue de secours, puis à la clé brute, donc ça se voit tout de suite sur la page. À chaque passage, la commande te liste ce qui reste à traduire.

Quelques règles à connaître :

- **Les clés construites à l'exécution** (`__('status.' . $status)`, `__($key)`), il peut pas les deviner. La commande te les liste avec leur fichier et leur ligne. S'il y a un préfixe en dur (`status.`), les clés qui commencent par lui sont jamais considérées comme inutilisées.
- **Une clé inutilisée est jamais supprimée sans `--prune`**, justement à cause des clés dynamiques : « inutilisée » veut parfois dire « utilisée, mais invisible au scan ».
- **Le domaine `skankydev`, il y touche pas** : c'est celui du framework.
- **Les dossiers régionaux** (`fr_CA/`) sont pas synchronisés : ils contiennent que des écarts.
- Le fichier est réécrit : le docblock d'en-tête est gardé, l'ordre des clés aussi, mais **les commentaires à l'intérieur du tableau sont perdus**.

## Locale et langue

Deux choses à pas confondre :

- la **langue** (`fr`) choisit le catalogue, donc le dossier ;
- la **locale** complète (`fr_CA`) sert au formatage : nombres, dates, devises, le `#` des pluriels.

Quand une clé est cherchée avec la locale `fr_CA`, le `Translator` essaie dans l'ordre :

```
lang/fr_CA/blog.php    optionnel : seulement les écarts québécois
lang/fr/blog.php       le catalogue principal
lang/{fallback}/...    la langue de secours (i18n.fallback)
la clé brute
```

En pratique, t'as juste des dossiers `fr/` et `en/`. Le jour où le Québec a besoin d'un mot différent, tu crées `fr_CA/blog.php` avec juste ce mot, et rien d'autre bouge.

Les locales s'écrivent au **format ICU**, `fr_FR` (avec un underscore). Le web, lui, utilise le format **BCP 47**, `fr-FR` (avec un tiret) : l'attribut `lang` du HTML, le header `Accept-Language`, `Intl` en JS. `Translator::setLocale()` accepte les deux, et `Translator::toLanguageTag()` (ou `$this->htmlLang()` dans une vue) fait la conversion dans l'autre sens.

## La config

```php
'i18n' => [
    'locale'    => 'en_US',              // locale par défaut
    'fallback'  => 'en',                 // langue de secours quand une clé manque
    'available' => ['en_US'],            // ce que ton projet accepte
    'path'      => LANG_FOLDER,          // src_front/lang
],
```

Ce sont les défauts du framework : **l'anglais**. Le starter accepte en plus le français (`'available' => ['en_US', 'fr_FR']`). Pour un projet en français, remets `'locale' => 'fr_FR'` et `'fallback' => 'fr'` dans ton `master.config.php`.

Attention à `available` : la config est fusionnée par `array_replace_recursive` ([04 Config](004-Config.md)), donc une liste est fusionnée **index par index**. C'est pour ça que le défaut du framework a qu'un seul élément : ta liste le remplace sans surprise.

## Choisir la langue

Le framework te donne les outils, mais **c'est ton application qui décide** où et comment s'en servir. Le starter le fait dans `config/bootstrap.php` :

```php
Translator::setLocale(LocaleNegotiator::negotiate());
```

`LocaleNegotiator::negotiate()` lit le header `Accept-Language`, respecte l'ordre de préférence (`q`), et te rend la meilleure locale de `i18n.available`, telle qu'elle est écrite dans ta config. Une langue demandée sans région (`fr`) ou avec une autre région (`fr-CA`) tombe sur `fr_FR`. Si rien correspond, c'est `i18n.locale`. En CLI, pas de header, donc la locale par défaut.

Pourquoi pas les fonctions de PHP ? `Locale::acceptFromHttp()` renvoie la préférence du navigateur sans regarder ce que t'as, et `Locale::lookup()` trouve pas `fr_FR` quand on demande `fr` (et en plus elle renvoie la valeur en minuscules).

Pour un **sélecteur de langue**, déplace l'appel dans un middleware ([07](007-Les-Middlewares.md)) placé **après** `Session` : le bootstrap tourne avant que la session soit démarrée.

```php
class LocaleMiddleware implements MiddlewareInterface {
    public function handle(Request $request, callable $next): mixed {
        Translator::setLocale(Session::get('locale') ?? LocaleNegotiator::negotiate());
        return $next($request);
    }
}
```

## Les helpers de vue

`HtmlView` embarque le trait `TranslatorHelper`, pour tout ce qui dépend de la locale (ici avec `fr_FR`) :

```php
<html lang="<?= $this->htmlLang() ?>">          <!-- fr-FR -->

<?= $this->number(1234.5) ?>                     <!-- 1 234,5 -->
<?= $this->number(3.1, 2) ?>                     <!-- 3,10 -->
<?= $this->currency(12.5) ?>                     <!-- 12,50 € -->
<?= $this->currency(12.5, 'GBP') ?>              <!-- 12,50 £GB -->
<?= $this->date($post->created) ?>               <!-- 12 oct. 2026 -->
<?= $this->date($post->created, pattern: 'd MMMM y') ?>  <!-- 12 octobre 2026 -->
```

`date()` prend un `DateTimeInterface`, une date Mongo (`UTCDateTime`), un timestamp ou une chaîne, et utilise la timezone par défaut (`timeHelper.timezone`). Les styles, ce sont les constantes de `IntlDateFormatter` (`SHORT`, `MEDIUM`, `LONG`, `FULL`, `NONE`), et un `pattern` ICU passe devant.

## Les messages du framework

Tout ce que le framework affiche à un utilisateur passe aussi par `__()`, dans le domaine réservé **`skankydev`** : les messages de validation ([13.2](013.2-La-Validation.md)), les erreurs d'upload ([05](005-La-Requete-Client.md)), les messages des middlewares (connexion requise, CSRF, trop de tentatives...) et toute la sortie de `php craft` ([17](017-Craft-et-CLI.md)). Ils sont livrés en anglais et en français dans `Publishable/lang/`.

Deux exceptions, voulues, qui restent **en anglais, en dur** :

- **les messages d'exception et les logs** : ils sont écrits pour le développeur, et une stack trace, ça se partage et ça se cherche mieux en anglais ;
- **les pages d'erreur** (`error/production.php`, `error/404.php`, `error/debug.php`) : elles s'affichent justement quand quelque chose a planté. Si elles passaient par `__()`, un fichier de langue cassé (une erreur de syntaxe, par exemple) ferait planter la page d'erreur elle-même, et on tournerait en boucle. Tu les veux en français ? Publie-les (`php craft publish -p=error`) et écris-les comme tu veux.

C'est le seul domaine avec un repli : tant que t'as pas de `skankydev.php` dans ton dossier de langues, le `Translator` lit celui du framework. Pour les personnaliser ([17 Craft et CLI](017-Craft-et-CLI.md)) :

```bash
php craft publish -p=lang
```

Ta copie remplace **le fichier entier** de la langue concernée, pas clé par clé : garde toutes les clés dedans. Le revers : quand une mise à jour du framework ajoute des messages, ta copie les a pas, et tu verras leurs clés brutes (`skankydev.cli.done`) à la place du texte. Il faut alors republier et reporter tes retouches. Et pour une langue que le framework livre pas (l'allemand, par exemple), pareil : tu crées `de/skankydev.php`.

## Et le front ?

Attention si tu veux réutiliser ces traductions côté Vue : **vue-i18n utilise pas ICU** (ses pluriels s'écrivent avec des `|`). Pour garder un seul format, la piste c'est `intl-messageformat` (FormatJS) côté front, alimenté par une route qui sert les catalogues en JSON. C'est pas encore fait.
