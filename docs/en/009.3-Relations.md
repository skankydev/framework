# 09.3 Relations and propagation

Two separate mechanisms, both declared on the `MasterCollection` side (never on the Document side):

- **relations** (`belongsTo` / `hasMany`): read a related document, without a manual query or a `$lookup`.
- **propagation**: keep the `EmbeddedSnapshot`s ([09.1](009.1-Persistable.md)) scattered across other collections up to date when the source changes.

## belongsTo / hasMany

You declare your relations in `relations()`, on the Collection:

```php
class PostCollection extends MasterCollection {
    public function relations(): array {
        return [
            'user'     => ['type' => 'belongsTo', 'collection' => UserCollection::class, 'key' => 'user_id'],
            'comments' => ['type' => 'hasMany',   'collection' => CommentCollection::class, 'key' => 'post_id'],
        ];
    }
}
```

- `belongsTo`: the key (`user_id`) is **on this document** (`Post`) and points to the other one (`User`). You get a document, or `null`.
- `hasMany`: the key (`post_id`) is **on the other document** (`Comment`) and points to this one. You get an array (empty if there's nothing).

The relation's name (`'user'`, `'comments'`) is what you read on the document, like a normal property:

```php
$post->user;      // a User instance, or null
$post->comments;  // an array of Comment
```

### Lazy loading, and in bulk

Without asking for anything, `$post->user` loads the relation **on demand** (one query on first access) and caches it on the instance: reading `$post->user` twice doesn't make two queries. Handy, but in a loop over posts, that's one query per post (the classic N+1).

To avoid it, preload in bulk with `with`. A single query per relation, no matter how many documents:

```php
$collection->find($filter, ['with' => ['user', 'comments']]);
$collection->findOne($filter, ['with' => ['user']]);
$collection->findById($id, ['with' => ['user']]);
$collection->paginate($filter, $paginateInfo, ['user']); // dedicated 3rd argument
```

If you get it wrong (unknown relation, or a `type` that's neither `belongsTo` nor `hasMany`), it throws an `\InvalidArgumentException` right away, instead of giving you a silent `null` or `[]`. That way, a typo in `with` shows up on the first test, not in production as an unexplainable "empty field".

A loaded relation is neither saved nor "dirty": it doesn't show up in the JSON or in what goes to the database, and it has no effect on `isDirty()`.

### The CrudMaker already declares them

For every `ObjectId` field of a Document generated by `crud-maker`, the Collection automatically gets the matching `belongsTo` entry, and the controller preloads the relation in `index()` with `with`. For the standard case (a simple foreign key), you have nothing to write by hand.

## Propagating EmbeddedSnapshots

A Collection declares where its documents are embedded elsewhere with `embeddedIn()`:

```php
class UserCollection extends MasterCollection {
    public function embeddedIn(): array {
        return [
            [
                'collection' => PostCollection::class,
                'field'      => 'author',
                'class'      => UserSnapshot::class,
                'sync'       => true,     // default: right away, otherwise off to the Queue
                'onDelete'   => 'keep',   // 'keep' (default) | 'mark' | 'unset'
            ],
        ];
    }
}
```

- `collection` / `field`: where to look for the snapshots to fix (`Post.author`).
- `class`: the `EmbeddedSnapshot` class used there.
- `sync`: when `true`, the resync happens right away, in the request that made the update. When `false`, it's pushed onto the Queue ([17](017-Queue-and-Jobs.md)) and the current request doesn't wait.
- `onDelete`: what happens to the existing snapshots when the source `User` is deleted:
  - `keep` (default): nothing, the snapshot stays frozen (the author of a deleted post keeps their name displayed).
  - `mark`: `_deleted` is set to `true` on the snapshot (you can display "deleted user", for example).
  - `unset`: the field (`author`) is removed from the target document altogether.

### When it fires

Automatically, you don't call anything yourself:

- **update** of a `User`: if the modified fields (`getDirty()`) touch a field copied by the snapshot (`UserSnapshot::syncedFields()`), the propagation kicks off. Changing a field that isn't copied (the password, for example) triggers nothing.
- **delete** (`deleteOne`, `deleteById`, or in bulk with `delete($filter)`): `onDelete` applies, unless it's `keep` (nothing to do in that case).

In both cases, it's one `SnapshotSyncJob` per target (`collection` / `field`) that does the work: right away if `sync`, or through the Queue otherwise.

`syncIndexes()` (called by `db-sync`, [16 Craft and CLI](016-Craft-and-CLI.md)) automatically creates an index on `{field}._id` on the target side for each `embeddedIn()` entry. The propagation needs it to find the snapshots quickly.

## Under the hood

- **The relation cache.** A loaded relation (through `with` or lazily) lives in a separate `WeakMap`, like the dirty tracking state ([09 Model](009-Model.md)). That's why it's missing from `bsonSerialize()` and `jsonSerialize()` and has no impact on `isDirty()`.
- **What the job does.** `SnapshotSyncJob` **reads the source again** when it runs, it doesn't carry the snapshot around. If the `User` still exists, it rebuilds `UserSnapshot` and does an `updateMany` on all the documents that carry its `_id` in `author._id`. If it's gone, `onDelete` applies. That makes it idempotent and order-independent: the last run always writes the current state, even if several jobs for the same `User` pile up in the Queue.
- **No cascade.** `updateMany()`, used by the job, bypasses the behaviors and the propagation. That's on purpose: otherwise a `SnapshotSyncJob` updating `Post`s could trigger a cascading propagation.
