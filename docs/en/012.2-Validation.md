# 12.2 Validation

## How it works

The `Validator` takes rules and an array of data, and tells you whether it passes:

```php
$validator = new Validator([
    'title' => 'required|max_length:120',
    'email' => 'required|email',
], $data);

if (!$validator->validate()) {
    $validator->errors(); // ['title' => ['The title field is required'], ...]
}
```

A rule is written either as a string with pipes (`'required|max_length:120'`), or as an array (`['required', 'max_length:120']`). Both forms are equivalent. A parameter after `:` (`max_length:120`) is passed to the rule, and several parameters are separated by a comma (`in:1,2,3`).

Each rule name (`required`, `email`...) is linked to a class through the `class.rules` config, same idea as `class.fields` and `class.middlewares`:

```php
'class' => [
    'rules' => [
        'required' => \SkankyDev\Validation\Rules\Required::class,
        'email'    => \SkankyDev\Validation\Rules\Email::class,
        // ...
    ],
],
```

For a given field, checking stops at the **first rule that fails**: no point stacking up every error message for the same field.

To read the errors: `errors()` gives you everything, grouped by field. `hasError('title')` and `error('title')` give you a field's first message.

The messages go through the translations (`skankydev` domain, [21 Internationalization](021-I18n.md)): they follow the user's language.

### Validation without a form

The `Validator` doesn't depend on the `FormBuilder`. You can use it on its own to validate any array: an API's JSON payload, a CSV import...

```php
$validator = new Validator(['email' => 'required|email'], $request->json());
if (!$validator->validate()) {
    return response(['errors' => $validator->errors()])->status(422);
}
```

On the `FormBuilder` side, `validate($data)` does exactly that behind the scenes: it builds the array of rules from the ones declared on each field (`add($name, $type, ['rules' => ...])`), runs a `Validator`, and passes the errors on to the form ([12 Forms](012-Forms.md)).

## The list of existing rules

| Rule | Checks |
|---|---|
| `required` | present, not empty (string or array) |
| `email` | valid email format |
| `numeric` | numeric value |
| `max_length:N` / `min_length:N` | string length (`mb_strlen`) |
| `max:N` / `min:N` | bounded numeric value |
| `regex:pattern` | matches the regular expression |
| `hex_color` | hex color (`#fff`, `#ffffff`) |
| `same:otherField` | identical to another field of the same data set |
| `confirmed` | identical to `{field}_confirmation` (password + confirmation, typically) |
| `unique:CollectionClass` | no document in that Collection already has this value (see below) |
| `file` | a properly uploaded file (valid `UploadedFile`) |
| `image` | a readable image, checked on the content |
| `mimes:jpg,png,webp` | the file's **real** type is in the list (`jpeg` = `jpg`) |
| `max_size:N` | the file doesn't exceed N KB |

The four file rules let an empty field through: add `required` if the file is mandatory. For a multiple field, every file in the list must pass. No need to put the files in `$data`: for each `file` field missing from the data, `FormBuilder::validate()` fetches the file from `Request::file()` on its own.

```php
$this->add('img', 'file', ['label' => 'Image', 'rules' => ['required', 'image', 'mimes:jpg,png,webp', 'max_size:2048']]);
```

All of them, except `required`, let an empty value through: a rule like `email` doesn't reject an optional field left empty. Only `required` takes care of that.

### `unique`, a bit special

It needs to know where to look: the Collection to query, and optionally the column if it differs from the field name:

```php
'slug' => 'required|unique:' . ArticleCollection::class,               // column = 'slug'
'slug' => 'required|unique:' . ArticleCollection::class . ',permalink', // different column
```

When editing, you have to exclude the current document, otherwise an update that doesn't change the value rejects itself. That's the 3rd parameter, the current document's `_id`:

```php
'slug' => 'required|unique:' . ArticleCollection::class . ',slug,' . $article->_id,
```

In practice, you build that in `build()` from `$this->getData()['_id']` (the `_id` is never submitted in the POST, it comes from the URL).

## Creating a new one

You extend `Rule`, and you implement `check()` and `message()`:

```php
class NotBanned extends Rule {
    public function check(string $field, mixed $value, array $data = []): bool {
        if ($this->isEmpty($value)) {
            return true; // optional: required takes care of the empty case
        }
        return !BannedWordCollection::getInstance()->exists($value);
    }

    public function message(string $field): string {
        return __('app.validation.not_banned', ['field' => $field]);
    }
}
```

The message goes through `__()` ([21 Internationalization](021-I18n.md)), with the key in your language file: `'not_banned' => 'The {field} field contains a banned word'`. The framework's rules do the same, in the `skankydev` domain. A hardcoded string works too, but it won't follow the user's language.

Then you register it under an alias in `class.rules`:

```php
'class' => [
    'rules' => [
        'not_banned' => \App\Validation\Rules\NotBanned::class,
    ],
],
```

`check()` receives the whole data set (`$data`), not just the field's value. That's useful for a rule that compares with another field (see `Same` and `Confirmed`, shipped with the framework).

## Under the hood

The "an empty value passes" behavior comes from `Rule::isEmpty()`, shared by the base class: that's what you call in your own rule to do the same.
