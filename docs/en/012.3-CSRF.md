# 12.3 CSRF

CSRF is the trap where a third-party site gets a logged-in user's browser to send a request to your app. To guard against it, I set up one token per session, compared on every request that modifies something (the *synchronizer token* pattern).

The `CsrfMiddleware` takes care of it. It's one of the two global middlewares by default (with `Session`, which runs just before it: a started session is needed to read and write the token, see [07 Middlewares](007-Middlewares.md)). So in most cases, you have nothing to do.

## What it checks, and when

Only the methods that modify something: `POST`, `PUT`, `PATCH`, `DELETE`. A `GET` is never concerned: CSRF only makes sense on an action that changes state on the server side.

The submitted token is looked for in two places, in this order:

1. the input's `_token` field (a regular form);
2. otherwise the `X-CSRF-Token` header (AJAX).

## The form case vs the AJAX case

**Form**: nothing to do. `FormBuilder::open()` adds `csrf_field()` on its own in every `<form>` tag with the POST method: a hidden `_token` field with the current value.

The token is created only once per session, the first time it's asked for, then reused as long as the session lives. It's not a single-use token per request.

**AJAX**: that one's on you. The framework gives you the server-side piece (`csrf_token()`, and it accepts the `X-CSRF-Token` header), but wiring up the automatic sending of that header on every `fetch` is the application's job. The classic way: put the token in a `<meta name="csrf-token">` tag in the layout, then wrap `fetch` on the project side so it reads that tag and adds the header.

## On failure

As with the other guard middlewares ([07](007-Middlewares.md)), the response depends on who's calling:

- the client expects JSON (`wantsJson()`, see [05](005-The-Client-Request.md)): a **419** in JSON (`{'ok': false, 'error': '...'}`);
- otherwise: a redirect to the previous page (`Referer`, or `/` by default) with an error flash (`withFlash('error', ...)`, see [11 Responses](011-Responses.md)).

In both cases, the controller is never reached: it's a middleware that short-circuits by returning a `Response` instead of calling `$next()`.

## Under the hood

```php
private const UNSAFE = ['POST', 'PUT', 'PATCH', 'DELETE'];
```

The submitted token is compared to the session's with `hash_equals()`, a constant-time comparison, not a naive `===`. That prevents a *timing attack* on the comparison itself.

```php
function csrf_token(): string {
    $token = Session::get('csrf_token');
    if (!is_string($token) || $token === '') {
        $token = (new Token())->getToken();
        Session::set('csrf_token', $token);
    }
    return $token;
}
```
