# 09.1 The Persistable (EmbeddedDocument · EmbeddedSnapshot)

## A pretty neat concept

A regular `MasterDocument` has an `_id` and lives in its own Collection. But sometimes, you just need a **structured, typed value** that lives *inside* another document: no `_id`, no Collection of its own, just a sub-object. That's `EmbeddedDocument`.

It works like a `MasterDocument` (`fill()` driven by the declared types, `DateTime` ⇄ `UTCDateTime`, enum ⇄ `->value`), without the collection part since there isn't one.

The nice part: you have nothing to do when reading back. An embedded object (or an array of embedded objects) comes back with the right class on its own (the "how" is in "Under the hood").

## The example we already have: Token

`SkankyDev\Utilities\Token` extends `EmbeddedDocument`. It's used as the value for email verification tokens, password reset tokens, etc:

```php
class Token extends EmbeddedDocument {
    public string $value = '';
    public int $time = 0;

    public function checkTime(int $life = TIME_HOUR): bool { ... }
    public function checkValue(string $value): bool { ... }
}
```

And on the `User` side:

```php
class User extends MasterDocument {
    public ?Token $reset_token   = null;
    public ?Token $verify_token  = null;
    public ?Token $remember_token = null;
}
```

You assign it like a normal object (`$user->reset_token = new Token()`), you save it with the `User` (`UserCollection::_save($user)`, no separate save for the Token), and when reading back you directly get a `Token` instance, not a raw array. `$user->reset_token->checkTime(TIME_HOUR)` works as is.

## The array case (not done here yet, but the principle works)

The same mechanism works for an **array** of `EmbeddedDocument`. Typically comments embedded in a post rather than a separate collection:

```php
class Comment extends EmbeddedDocument {
    public string $author  = '';
    public string $content = '';
    public ?DateTime $created_at = null;
}

class Post extends MasterDocument {
    /** @var Comment[] */
    public array $comments = [];
}
```

When reading, `$post->comments` is an array of real `Comment` instances, not `stdClass` objects or associative arrays.

When should you pick this? If the comments don't need to exist without their post (no global search on them, no independent pagination), it's the right choice. Otherwise, a real separate Collection is a better fit.

## EmbeddedSnapshot: a copy that keeps itself up to date

`Comment.author` above is a frozen embedded value: handy for a value that changes little or not at all. But imagine you embed a copy of a `User` (name, avatar) in `Post.author` to avoid a `$lookup` on every display. Then you want the copy to update when the user changes their avatar.

That's the job of `EmbeddedSnapshot` (which extends `EmbeddedDocument`). It's MongoDB's *Extended Reference* pattern, with the syncing handled by the framework rather than by hand.

```php
class UserSnapshot extends EmbeddedSnapshot {
    public string $name   = '';
    public string $avatar = '';
}
```

The public properties you declare *are* the fields copied from the source, so there's no separate config to maintain. `EmbeddedSnapshot` also adds two fields you never declare yourself:

- `_id`: the `_id` of the source document (`User`), to find the snapshot from it.
- `_deleted`: `true` if the source has been deleted since (see `onDelete` in [09.3](009.3-Relations.md)).

```php
$post->author = new UserSnapshot($user); // copies name + avatar from $user, plus its _id
```

`$user` must have been saved (have an `_id`), otherwise it throws a `\LogicException`: a snapshot without an identifiable source would make no sense.

Who gets resynced, and how, is declared on the `UserCollection` side (not on `Post` nor on `UserSnapshot`): it's the source that knows where its copies are scattered. All the details are in [09.3 Relations and propagation](009.3-Relations.md).

## Under the hood

The Mongo driver stores a `__pclass` field next to the data, which tells it which PHP class to rebuild when reading. That's what makes an embedded object, or each element of an array of embedded objects, come back typed without you dealing with it.
