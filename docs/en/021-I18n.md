# 21 Internationalization (i18n)

To translate the interface, SkankyDev relies on **ext/intl** (ICU), not on gettext. Gettext depends on the locales installed on the system, keeps the `.mo` files cached until PHP restarts, and its plurals are limited. Intl formats messages, numbers and dates properly, but doesn't store the translations: that's the framework's `Translator`, with plain PHP files.

This chapter covers translating the **interface** (labels, messages). Content (a blog post in several languages) is a different topic, handled in your Documents.

## Translating

```php
<dt><?= __('admin.blog.title') ?></dt>
<dd><?= e($post->name) ?></dd>

<p><?= __('blog.post.by', ['name' => e($post->author)]) ?></p>
```

`__()` **always returns a string**. If the key doesn't exist (or if the message is badly written), you get the key itself, `blog.post.by`: the page still displays, and you can see right away what's missing. In debug, it's also written to `logs/{date}-i18n.log`.

`__()` does **no escaping**: the text of the language files is yours, it's safe, but an argument coming from the user must go through `e()`, like everywhere else.

## Language files

They're in `src_front/lang/` (`i18n.path`, `LANG_FOLDER` constant), one folder per language, **one file per domain**. The first segment of the key is the file:

```
src_front/lang/
  fr/
    app.php        __('app.welcome')
    blog.php       __('blog.post.count')
  en/
    app.php
    blog.php
```

The example is in French, because it shows plurals and gender agreement better:

```php
// src_front/lang/fr/blog.php
return [
    'label' => 'Titre',
    'post'  => [
        'title' => 'Article : {title}',
        'count' => '{count, plural, =0 {Aucun article} one {# article} other {# articles}}',
        'by'    => '{gender, select, female {Écrite par {name}} other {Écrit par {name}}}',
    ],
];
```

The rest of the key follows the usual dot notation (like `Config::get()`). A file is only loaded when it's needed, and only once per request.

### One key = one usage, not one word

The key identifies a spot in the interface, the value holds the exact text to display, capitals included. No `Title` / `title` duplicates: if you need both, you have two usages, so two keys.

And above all, **you translate whole sentences**, never pieces glued back together:

```php
// ❌ works in English, breaks in other languages (word order, agreement)
__('word.the') . ' ' . __('word.field') . ' ' . __('word.required')

// ✅
'required' => 'The {field} field is required',
```

For a purely visual transformation (a title in capitals), it's CSS (`text-transform`), not a new key.

## The ICU MessageFormat format

Messages use the ICU format, the same as Symfony or `intl-messageformat` in JS:

- **`{name}`**: a variable, a single brace (not `:name` like Laravel).
- **`{count, plural, one {...} other {...}}`**: plurals. `#` is replaced by the number, formatted for the locale (`1 234` in fr, `1,234` in en). The rules come from CLDR, there's nothing to code: **in French, `0` is singular** ("0 article"), in English it isn't ("0 posts"). `=0 {...}` forces a text for a specific value.
- **`{gender, select, female {...} other {...}}`**: a choice on a value. `other` is mandatory.

A trap: in ICU, **the straight apostrophe `'` is an escape character**. `l'article` goes through, but `'{name}'` is displayed as is, without replacing the variable. The simplest fix: use the typographic apostrophe `’` in your translations, and the problem goes away.

## Keeping the files up to date: `lang-sync`

Rather than copying keys by hand into every language, `php craft lang-sync` reads your code and updates the language files:

```bash
php craft lang-sync              # adds the missing keys
php craft lang-sync --dry-run    # shows what it would do, without writing anything
php craft lang-sync --prune      # also removes the unused keys
php craft lang-sync --check      # writes nothing, exits with an error if something is missing (for CI)
```

It scans `src/{Module}/` of every module and the views folder, and finds all the `__('domain.key')` calls. For each language in `i18n.available` (and the fallback), it adds the missing keys in `lang/{language}/{domain}.php` with the value **`null`**:

```php
return [
    'title' => 'Title',
    'post'  => [
        'count' => null,
    ],
];
```

`null` means "not translated yet": the `Translator` moves on to the fallback language, then to the raw key, so it shows up on the page right away. On every run, the command lists what's left to translate.

A few rules to know:

- **Keys built at runtime** (`__('status.' . $status)`, `__($key)`) can't be guessed. The command lists them with their file and line. When there's a literal prefix (`status.`), keys starting with it are never considered unused.
- **An unused key is never removed without `--prune`**, precisely because of dynamic keys: "unused" sometimes means "used, but invisible to the scan".
- **The `skankydev` domain is never touched**: it's the framework's.
- **Regional folders** (`fr_CA/`) aren't synced: they only hold differences.
- The file is rewritten: the header docblock is kept, and so is the order of the keys, but **comments inside the array are lost**.

## Locale and language

We tell two things apart:

- the **language** (`fr`) picks the catalog, so the folder;
- the full **locale** (`fr_CA`) is used for formatting: numbers, dates, currencies, the `#` of plurals.

When a key is looked up with the `fr_CA` locale, the `Translator` tries, in order:

```
lang/fr_CA/blog.php    optional: only the Quebec differences
lang/fr/blog.php       the main catalog
lang/{fallback}/...    the fallback language (i18n.fallback)
the raw key
```

In practice, you only have `fr/` and `en/` folders. The day Quebec needs a different word, you create `fr_CA/blog.php` with just that word, and nothing else changes.

Locales are written in **ICU format**, `fr_FR` (with an underscore). The web uses the **BCP 47** format, `fr-FR` (with a hyphen): HTML's `lang` attribute, the `Accept-Language` header, `Intl` in JS. `Translator::setLocale()` accepts both, and `Translator::toLanguageTag()` (or `$this->htmlLang()` in a view) does the reverse conversion.

## The config

```php
'i18n' => [
    'locale'    => 'en_US',              // default locale
    'fallback'  => 'en',                 // fallback language when a key is missing
    'available' => ['en_US'],            // what your project accepts
    'path'      => LANG_FOLDER,          // src_front/lang
],
```

These are the framework's defaults: **English**. The starter also accepts French (`'available' => ['en_US', 'fr_FR']`). For a French project, set `'locale' => 'fr_FR'` and `'fallback' => 'fr'` in your `master.config.php`.

Careful with `available`: the config is merged with `array_replace_recursive` ([04 Config](004-Config.md)), so a list is merged **index by index**. The framework's default has a single element so that your list replaces it without surprises.

## Choosing the language

The framework provides the tools, **your application decides** where and how to use them. The starter does it in `config/bootstrap.php`:

```php
Translator::setLocale(LocaleNegotiator::negotiate());
```

`LocaleNegotiator::negotiate()` reads the `Accept-Language` header, respects the order of preference (`q`), and returns the best locale from `i18n.available`, as written in your config. A language requested without a region (`fr`) or with another region (`fr-CA`) finds `fr_FR`. If nothing matches, it's `i18n.locale`. In the CLI, there's no header, so it's the default locale.

We don't use `Locale::acceptFromHttp()` (it returns the browser's preference without taking into account what you have), nor `Locale::lookup()` (it doesn't find `fr_FR` when `fr` is requested, and returns the value in lowercase).

For a **language selector**, move the call into a middleware ([07](007-Middlewares.md)) placed **after** `Session`: the bootstrap runs before the session is started.

```php
class LocaleMiddleware implements MiddlewareInterface {
    public function handle(Request $request, callable $next): mixed {
        Translator::setLocale(Session::get('locale') ?? LocaleNegotiator::negotiate());
        return $next($request);
    }
}
```

## View helpers

`HtmlView` includes the `TranslatorHelper` trait, for everything that depends on the locale (here with `fr_FR`):

```php
<html lang="<?= $this->htmlLang() ?>">          <!-- fr-FR -->

<?= $this->number(1234.5) ?>                     <!-- 1 234,5 -->
<?= $this->number(3.1, 2) ?>                     <!-- 3,10 -->
<?= $this->currency(12.5) ?>                     <!-- 12,50 € -->
<?= $this->currency(12.5, 'GBP') ?>              <!-- 12,50 £GB -->
<?= $this->date($post->created) ?>               <!-- 12 oct. 2026 -->
<?= $this->date($post->created, pattern: 'd MMMM y') ?>  <!-- 12 octobre 2026 -->
```

`date()` accepts a `DateTimeInterface`, a Mongo date (`UTCDateTime`), a timestamp or a string, and uses the default timezone (`timeHelper.timezone`). The styles are the `IntlDateFormatter` constants (`SHORT`, `MEDIUM`, `LONG`, `FULL`, `NONE`), an ICU `pattern` takes precedence.

## The framework's messages

Everything the framework shows to a user also goes through `__()`, in the reserved **`skankydev`** domain: validation messages ([12.2](012.2-Validation.md)), upload errors ([05](005-The-Client-Request.md)), middleware messages (login required, CSRF, too many attempts...), the password field, and all the output of `php craft` ([16](016-Craft-and-CLI.md)). They're shipped in English and French in `Publishable/lang/`.

Two exceptions, on purpose, that stay **in English, hardcoded**:

- **exception messages and logs**: they're written for the developer, and a stack trace is easier to share and search for in English;
- **the error pages** (`error/production.php`, `error/404.php`, `error/debug.php`): they show up precisely when something has crashed. If they went through `__()`, a broken language file (a syntax error, for example) would crash the error page too, and we'd go round in circles. To have them in another language, publish them (`php craft publish -p=error`) and write them however you like.

It's the only domain with a fallback: as long as you don't have a `skankydev.php` in your language folder, the `Translator` reads the framework's. To customize them ([16 Craft and CLI](016-Craft-and-CLI.md)):

```bash
php craft publish -p=lang
```

Your copy replaces **the whole file** for the language concerned, not key by key: keep all the keys in it. Consequence: when a framework update adds messages, your copy doesn't have them, and you'll see their raw keys (`skankydev.cli.done`) instead of the text. You then have to publish again and carry over your tweaks. And for a language the framework doesn't ship (German, for example), it's the same: create `de/skankydev.php`.

## And the front end?

Careful if you want to reuse these translations on the Vue side: **vue-i18n doesn't use ICU** (its plurals are written with `|`). To keep a single format, the way to go is `intl-messageformat` (FormatJS) on the front end, fed by a route that serves the catalogs as JSON. It's not done yet.
