# 09.1 Le Persistable (EmbeddedDocument · EmbeddedSnapshot)

## Un concept bien sympathique

Un `MasterDocument` normal a un `_id` et vit dans sa propre Collection. Mais des fois, t'as juste besoin d'une **valeur structurée et typée** qui vit *dans* un autre document : pas de `_id`, pas de Collection à elle, juste un sous-objet. C'est `EmbeddedDocument`.

Il fonctionne comme un `MasterDocument` (`fill()` piloté par les types déclarés, `DateTime` ⇄ `UTCDateTime`, enum ⇄ `->value`), sans la partie collection puisqu'il n'y en a pas.

Le côté sympa : tu n'as rien à faire à la relecture. Un objet embarqué (ou un tableau d'objets embarqués) revient tout seul avec la bonne classe (le « comment » est dans « Sous le capot »).

## L'exemple qu'on a déjà : Token

`SkankyDev\Utilities\Token` étend `EmbeddedDocument`. Il sert de valeur pour les tokens de vérification d'email, de reset de mot de passe, etc :

```php
class Token extends EmbeddedDocument {
    public string $value = '';
    public int $time = 0;

    public function checkTime(int $life = TIME_HOUR): bool { ... }
    public function checkValue(string $value): bool { ... }
}
```

Et côté `User` :

```php
class User extends MasterDocument {
    public ?Token $reset_token   = null;
    public ?Token $verify_token  = null;
    public ?Token $remember_token = null;
}
```

Tu l'assignes comme un objet normal (`$user->reset_token = new Token()`), tu le sauves avec le `User` (`UserCollection::_save($user)`, pas de save séparé pour le Token), et à la relecture tu récupères directement une instance de `Token`, pas un tableau brut. `$user->reset_token->checkTime(TIME_HOUR)` marche tel quel.

## Le cas tableau (pas encore fait ici, mais le principe marche)

Le même mécanisme fonctionne pour un **tableau** d'`EmbeddedDocument`. Typiquement des commentaires embarqués dans un post plutôt qu'une collection à part :

```php
class Comment extends EmbeddedDocument {
    public string $author  = '';
    public string $content = '';
    public ?DateTime $created_at = null;
}

class Post extends MasterDocument {
    /** @var Comment[] */
    public array $comments = [];
}
```

À la lecture, `$post->comments` est un tableau de vraies instances `Comment`, pas des `stdClass` ni des tableaux associatifs.

Quand choisir ça ? Si les commentaires n'ont pas besoin d'exister sans leur post (pas de recherche globale dessus, pas de pagination indépendante), c'est le bon choix. Sinon, une vraie Collection à part est plus indiquée.

## EmbeddedSnapshot : une copie qui se tient à jour toute seule

`Comment.author` ci-dessus, c'est un embedded figé : pratique pour une valeur qui bouge peu ou pas. Mais imagine que tu embarques une copie d'un `User` (nom, avatar) dans `Post.author` pour éviter un `$lookup` à chaque affichage. Là, tu veux que la copie se mette à jour quand l'utilisateur change son avatar.

C'est le rôle d'`EmbeddedSnapshot` (qui étend `EmbeddedDocument`). C'est le pattern MongoDB *Extended Reference*, avec la synchronisation prise en charge par le framework plutôt qu'à la main.

```php
class UserSnapshot extends EmbeddedSnapshot {
    public string $name   = '';
    public string $avatar = '';
}
```

Les propriétés publiques que tu déclares *sont* les champs copiés depuis la source, donc pas de config séparée à maintenir. `EmbeddedSnapshot` ajoute aussi deux champs que tu ne déclares jamais toi-même :

- `_id` : l'`_id` du document source (`User`), pour retrouver la snapshot depuis lui.
- `_deleted` : `true` si la source a été supprimée depuis (voir `onDelete` dans [09.3](009.3-Relations.md)).

```php
$post->author = new UserSnapshot($user); // copie name + avatar depuis $user, plus son _id
```

`$user` doit avoir été sauvé (avoir un `_id`), sinon ça lève une `\LogicException` : une snapshot sans source identifiable n'aurait aucun sens.

Qui se resynchronise, et comment, c'est déclaré côté `UserCollection` (pas côté `Post` ni côté `UserSnapshot`) : c'est la source qui sait où ses copies sont éparpillées. Tout le détail est dans [09.3 Relations et propagation](009.3-Relations.md).

## Sous le capot

Le driver Mongo stocke un champ `__pclass` à côté des données, qui lui dit quelle classe PHP reconstruire à la lecture. C'est ce qui fait qu'un objet embarqué, ou chaque élément d'un tableau d'objets embarqués, revient typé sans que tu t'en occupes.
