# 12.2 La Validation

## Comment ça marche

Le `Validator` prend des règles et un tableau de données, et te dit si ça passe :

```php
$validator = new Validator([
    'title' => 'required|max_length:120',
    'email' => 'required|email',
], $data);

if (!$validator->validate()) {
    $validator->errors(); // ['title' => ['Le champ title est requis'], ...]
}
```

Une règle s'écrit soit en chaîne avec des pipes (`'required|max_length:120'`), soit en tableau (`['required', 'max_length:120']`). Les deux formes sont équivalentes. Un paramètre après `:` (`max_length:120`) est passé à la règle, et plusieurs paramètres se séparent par une virgule (`in:1,2,3`).

Chaque nom de règle (`required`, `email`...) est relié à une classe par la config `class.rules`, même principe que `class.fields` et `class.middlewares` :

```php
'class' => [
    'rules' => [
        'required' => \SkankyDev\Validation\Rules\Required::class,
        'email'    => \SkankyDev\Validation\Rules\Email::class,
        // ...
    ],
],
```

Pour un champ donné, la vérification s'arrête à la **première règle qui échoue** : pas la peine d'empiler tous les messages d'erreur d'un même champ.

Pour lire les erreurs : `errors()` te donne tout, groupé par champ. `hasError('title')` et `error('title')` te donnent le premier message d'un champ.

### Validation sans form

Le `Validator` ne dépend pas du `FormBuilder`. Tu peux t'en servir seul pour valider n'importe quel tableau : le payload JSON d'une API, un import CSV...

```php
$validator = new Validator(['email' => 'required|email'], $request->json());
if (!$validator->validate()) {
    return response(['errors' => $validator->errors()])->status(422);
}
```

Côté `FormBuilder`, `validate($data)` fait exactement ça en coulisses : il construit le tableau de règles à partir de celles déclarées sur chaque champ (`add($name, $type, ['rules' => ...])`), lance un `Validator`, et répercute les erreurs sur le form ([12 Les Forms](012-Les-Forms.md)).

## La liste des règles existantes

| Règle | Vérifie |
|---|---|
| `required` | présent, non vide (chaîne ou tableau) |
| `email` | format email valide |
| `numeric` | valeur numérique |
| `max_length:N` / `min_length:N` | longueur de chaîne (`mb_strlen`) |
| `max:N` / `min:N` | valeur numérique bornée |
| `regex:pattern` | correspond à l'expression régulière |
| `hex_color` | couleur hexa (`#fff`, `#ffffff`) |
| `same:autreChamp` | identique à un autre champ du même jeu de données |
| `confirmed` | identique à `{champ}_confirmation` (mot de passe + confirmation, typiquement) |
| `unique:CollectionClass` | aucun document de cette Collection n'a déjà cette valeur (voir plus bas) |
| `file` | un fichier correctement envoyé (`UploadedFile` valide) |
| `image` | une image lisible, vérifiée sur le contenu |
| `mimes:jpg,png,webp` | le type **réel** du fichier fait partie de la liste (`jpeg` = `jpg`) |
| `max_size:N` | le fichier ne dépasse pas N Ko |

Les quatre règles de fichiers laissent passer un champ vide : ajoute `required` si le fichier est obligatoire. Pour un champ multiple, chaque fichier de la liste doit passer. Pas besoin de mettre les fichiers dans `$data` : pour chaque champ `file` absent des données, `FormBuilder::validate()` va chercher le fichier dans `Request::file()` tout seul.

```php
$this->add('img', 'file', ['label' => 'Image', 'rules' => ['required', 'image', 'mimes:jpg,png,webp', 'max_size:2048']]);
```

Toutes, sauf `required`, laissent passer une valeur vide : une règle comme `email` ne rejette pas un champ optionnel laissé vide. Seul `required` s'en charge.

### `unique`, un peu spéciale

Elle a besoin de savoir où chercher : la Collection à interroger, et éventuellement la colonne si elle diffère du nom du champ :

```php
'slug' => 'required|unique:' . ArticleCollection::class,               // colonne = 'slug'
'slug' => 'required|unique:' . ArticleCollection::class . ',permalink', // colonne différente
```

En édition, il faut exclure le document courant, sinon un update qui ne change pas la valeur se rejette lui-même. C'est le 3e paramètre, l'`_id` du document en cours :

```php
'slug' => 'required|unique:' . ArticleCollection::class . ',slug,' . $article->_id,
```

En pratique, tu construis ça dans `build()` à partir de `$this->getData()['_id']` (l'`_id` n'est jamais soumis dans le POST, il vient de l'URL).

## En créer une nouvelle

Tu étends `Rule`, et tu implémentes `check()` et `message()` :

```php
class NotBanned extends Rule {
    public function check(string $field, mixed $value, array $data = []): bool {
        if ($this->isEmpty($value)) {
            return true; // optionnelle : required s'occupe du cas vide
        }
        return !BannedWordCollection::getInstance()->exists($value);
    }

    public function message(string $field): string {
        return "Le champ {$field} contient un terme interdit";
    }
}
```

Puis tu l'enregistres sous un alias dans `class.rules` :

```php
'class' => [
    'rules' => [
        'not_banned' => \App\Validation\Rules\NotBanned::class,
    ],
],
```

`check()` reçoit tout le jeu de données (`$data`), pas juste la valeur du champ. C'est utile pour une règle qui compare avec un autre champ (voir `Same` et `Confirmed`, livrées avec le framework).

## Sous le capot

Le comportement « une valeur vide passe » vient de `Rule::isEmpty()`, commun à la classe de base : c'est ce que tu appelles dans ta propre règle pour faire pareil.
